# v1.1.1 Plugin Interaction Emulation Gap Report

Date: 2026-07-03

## Scope

This report re-emulates the v1.1.1 interaction/chat/runtime-composer rules against the current ThinkIO rebuild and the planned VS Code plugin structure.

The review focuses on:

- how ThinkIO interacts with a model;
- how model output returns to ThinkIO;
- how plugin chat/composer activity is logged;
- how new task creation should work from chat/model interaction;
- what should be candidate work now versus idea work for review.

## Emulation Findings

### 1. Interaction logs exist in v1.1.1 vocabulary, but are not yet modeled directly

The v1.1.1 terminology map normalizes `prompt/reply log` and `prompt reply log` to `interaction log`.

Current rebuild status:

- TASK-050 says chat sessions attach to runtime records without becoming canonical state.
- TASK-056 says chat/model interaction must remain attached to runtime records.
- No explicit plugin interaction log record model exists yet.

Gap:

- The plugin needs a structured interaction log boundary before chat-like interaction becomes active.

Decision:

- Required candidate task: TASK-059.

### 2. Canonical event history must stay separate from prompt transcripts and plugin traces

The v1.1.1 runtime event log primitive says the canonical event log must stay separate from adapter convenience logs, UI traces, prompt transcripts, and plugin cache views.

Current rebuild status:

- Process ledger, intake, provider ingest, and interaction surface boundaries exist.
- The plugin-specific split between canonical events, process ledger, interaction logs, and UI traces is not explicit enough.

Gap:

- Without a plugin interaction log boundary, a VS Code composer could accidentally make conversation history feel authoritative.

Decision:

- Required candidate task: TASK-059.

### 3. Transcript-grade preservation is optional and request-driven

v1.1.1 repeatedly marks full prompt/reply transcript-grade preservation as optional, mainly needed for Option 3 continuity, audit-grade recovery, or explicit user request.

Current rebuild status:

- Normal closeout and history validation are present.
- No explicit policy says when transcript-grade plugin logging is enabled or disabled.

Gap:

- The MVP should not require full transcript capture, but the policy should be reviewed.

Decision:

- Idea task for review: TASK-062.

### 4. Runtime interaction is a composer/result surface, not a generic chat transcript

The v1.1.1 runtime composer annex defines a `RuntimeInteractionRegion` with context bar, result view, composer, and follow-up actions. It says no full conversation history is required in Wave 1, and warns against a generic chatbot transcript.

Current rebuild status:

- TASK-051 and `docs/vscode-plugin-runtime-shell.md` establish a plugin model boundary.
- TASK-056 and TASK-057 cover command/data bridge and cross-view commands.
- No separate plugin runtime composer/result surface task exists yet.

Gap:

- The VS Code plugin needs an explicit composer/result contract so model interaction appears as governed runtime results, not loose chat.

Decision:

- Required candidate task: TASK-061.

### 5. New task creation from chat must be proposal-first

The current user goal requires ThinkIO to gather information through model/chat interaction and create new tasks from it.

Current rebuild status:

- TASK-046 defines external model/third-party intake review.
- TASK-056 defines command routing.
- TASK-057 now includes mode switching, add task, save task, deferring work, proposal review, and approval commands.
- No dedicated chat-to-task proposal pipeline exists.

Gap:

- The plugin needs a governed path for asking clarifying questions, drafting task proposals, reviewing them, and only then saving canonical task JSON/card state.

Decision:

- Required candidate task: TASK-060.

### 6. Historical transcripts/logs should remain evidence until reviewed

v1.1.1 has historical prompt/reply/session-continuity material, but also repeatedly warns that historical sources do not become authority automatically.

Current rebuild status:

- Package history and archive boundaries exist.
- No policy exists for importing old chat logs into the new interaction log model.

Gap:

- Historical log import is useful but not required for the plugin MVP.

Decision:

- Idea task for review: TASK-063.

## Candidate Tasks Added

### TASK-059: Add plugin interaction log boundary model

Required because the plugin composer/chat path needs a structured interaction log that cannot be confused with canonical event history or task state.

### TASK-060: Add chat-to-task proposal pipeline

Required because the plugin must let ThinkIO gather information and create new task proposals from model/chat interaction while keeping save/promote actions governed.

### TASK-061: Add plugin runtime composer result surface

Required because v1.1.1 defines runtime interaction as a governed composer/result surface, not a generic chat transcript.

## Idea Tasks Added For Review

### TASK-062: Evaluate trace mode transcript preservation policy

Review later unless the plugin MVP requires transcript-grade capture.

### TASK-063: Evaluate historical chat log import policy

Review later unless old transcripts need to be imported into the new interaction-log structure.

## Recommended Next Order

1. TASK-059
2. TASK-061
3. TASK-060
4. TASK-062 if audit/trace policy becomes necessary
5. TASK-063 if historical chat import becomes necessary

## Current Emulation Result

The current rebuild is aligned with v1.1.1 at the high-level boundary: chat is non-canonical, model interaction is governed, and plugin views must not write directly.

The missing piece is plugin-level specificity. TASK-059 through TASK-061 fill that gap by making the interaction log, composer/result surface, and chat-to-task proposal flow explicit before implementation.
